## Ergebnis

Das Projekt enthält eine umfangreiche React-Oberfläche und einen teilweise implementierten lokalen Prozessmanager. Zahlreiche angezeigte Funktionen sind Simulationen. Eine erfolgreiche Kompilierung bestätigt deshalb nicht die Funktionalität des Produkts. Insbesondere ist der ursprüngliche Stand wegen fehlender Backend-Authentifizierung und ungeschützter Dateipfade nicht für öffentlich erreichbaren Betrieb geeignet.

Dieser Bericht beschreibt den ORIGINALSTAND. Nachfolgende Reparaturen werden gesondert dokumentiert. Der Benutzer hat während der Prüfung ausdrücklich auch Reparaturen beauftragt.

## Durchgeführte Prüfungen

- Git-Clone und Quellcodeprüfung von Backend, Installer, Datenhaltung und wichtigen Bedienabläufen.
- Abhängigkeiten unter Node 24.19.0 / pnpm 11.25.0 installiert, ohne Installationsskripte von Paketen auszuführen.
- E: ist exFAT. Die normale pnpm-Installation scheitert an Verzeichnis-Symlinks. `--node-linker=hoisted` funktioniert. Der pnpm-11-Aufruf `run` versucht hier erneut eine Standardinstallation; die eigentlichen Prüfprogramme wurden deshalb direkt ausgeführt.
- `node node_modules/typescript/bin/tsc --noEmit`: bestanden.
- `node node_modules/vite/bin/vite.js build`: bestanden; Warnungen zu `__dirname` bei künftigem nativem Config-Loader und zum großen Hauptbundle (820,48 kB).
- Zehn Fehler in den tatsächlichen ursprünglichen Backend-Handlern reproduziert, mit isolierten Dateifixtures und simulierten Prozessobjekten. Siehe `backend-reproductions.json` und `reproduce-backend.mjs`.
- Keine echten HTTP-Dienste, Spielserver, Systeminstaller oder SteamCMD-Prozesse gestartet. Kein Live-Test von Spielinstallationen, RCON, Zahlungsdiensten oder fremden Webhooks. Das Testprogramm bindet keinen Port.

## Bestätigte Backend-Fehler

| ID | Schwere | Befund und Beleg im ursprünglichen Code |
|---|---|---|
| NO-AUTH | Kritisch | Keine Authentifizierung/Rechteprüfung vor den API-Routen, `server.ts:18`, `server.ts:457`, `server.ts:736`. Create ohne Session akzeptiert. |
| PATH-READ | Kritisch | ID `..` verlässt das Instanzverzeichnis und liest ein benachbartes Log, `server.ts:405`. Im Test reproduziert. |
| PATH-WRITE | Kritisch | Create mit `../escaped` erzeugt Dateien außerhalb des Serverwurzelverzeichnisses, `server.ts:736`. Im Test reproduziert. |
| EXEC-ESCAPE | Kritisch | Bevorzugte Executable darf `../../outside-game.exe` sein; Zugriff ohne Berechtigungsprüfung. Tatsächlicher Spawn im Test ersetzt, `server.ts:289`, `server.ts:597`. |
| CHILD-ERROR | Hoch | Bei Spielstarts fehlt ein `error`-Listener. Ein asynchroner Spawnfehler kann als unbehandeltes Event den Manager beenden, `server.ts:540`, `server.ts:625`. Listeneranzahl 0 reproduziert. |
| RESTART | Hoch | Backend-`restart` beendet den alten Prozess und meldet Erfolg, startet aber keinen Ersatz, `server.ts:695`. Reproduziert. |
| EXIT-RACE | Hoch | Altes `exit`-Event löscht unter derselben ID die Registrierung eines neuen Prozesses, `server.ts:580`, `server.ts:657`. Reproduziert. |
| KILL | Hoch | Backend-`kill` verwendet den normalen Stopppfad, sendet nicht sofort SIGKILL, `server.ts:664`. Reproduziert. |
| STEAM-SIGNAL | Hoch | SteamCMD-Ende mit Code `null`/Signal wird als erfolgreiche Installation gewertet, `server.ts:259`. Reproduziert. |
| ARG-QUOTING | Mittel | `split(' ')` zerstört Anführungszeichen in Startargumenten, `server.ts:621`. Reproduziert. |

Weitere strukturelle Probleme: Start- und Installationsrouten besitzen keine Instanzsperren über asynchrone Schritte; parallele Starts können doppelte Prozesse erzeugen. Die Prozessregistrierung ist nur im RAM und wird nach einem Managerneustart nicht wiederhergestellt (`server.ts:40`). PID-Erzeugung wird mit erfolgreichem Spielstart verwechselt. Portbelegung wird beim tatsächlichen Instanzstart nicht geprüft. `stop` ist als Eingabebefehl nicht für alle Spiele passend. Es fehlt eine Begrenzung/Validierung von RAM, Port, Befehlen und Instanzdaten. Instanzmetadaten werden nicht dauerhaft im Backend gespeichert. Fehlende Dateisystemrechte werden in der Protokollierung teilweise verschluckt.

Der Linux-Installer läuft als root, richtet den Manager ebenfalls als root ein und öffnet Port 3000 (`install.sh:170`, `install.sh:139`). Zusammen mit den oben bestätigten Fehlern könnten unbefugte Requests Aktionen mit den Rechten dieses Dienstes ausführen. Der HTTP-Listener ist nicht auf Loopback beschränkt (`server.ts:1023`).

## Bedienabläufe und Funktionsumfang

| Bereich | Tatsächlicher ursprünglicher Stand / Fehler |
|---|---|
| Anmeldung | Login prüft nur den Namen/die E-Mail und ignoriert das Passwort (`LoginModal.tsx:30`). Browser kann Rollen wechseln; keine echte Session. |
| Server erstellen | Browser meldet Erfolg vor Backendantwort und ignoriert Fehler (`App.tsx:705`). Instanzdaten, Eigentümer und Verträge leben in localStorage. |
| Starten | Netz-/JSON-Fehler führen trotzdem nach Timer zum Status „running“ und erfundenem Port-Bindelog (`App.tsx:217`). |
| Status | Log-Polling ignoriert Backend-`isRunning`/PID (`App.tsx:194`). Abstürze werden nicht zuverlässig im Status abgebildet. |
| Stoppen | Antwortstatus wird nicht ausgewertet, danach erfundener Exit-Code 0 (`App.tsx:305`). |
| Kill | UI ändert ausschließlich Browserzustand und sendet keine Backendanfrage (`App.tsx:340`). |
| Löschen | Entfernt nur Browserobjekte/CRM-Einträge, keine Prozesse/Dateien auf dem Host (`App.tsx:366`). |
| Konsole | Backend-stdin existiert; Frontend erfindet Antworten für TPS, Spieler, Speichern, OP, Ban und weitere Befehle (`App.tsx:443`). Kein implementierter RCON-Client. |
| Dateimanager | Mock-Dateibaum; Speichern, Anlegen, Löschen und Upload nur in UI (`FileManagerView.tsx:37`, `:243`, `:286`, `:309`; `App.tsx:625`). |
| SFTP | Angezeigte Beispiel-Zugangsdaten, kein SFTP-Daemon im Projekt. |
| Backups | Beispielarchive und erfundene Dateigrößen. Erstellen/Restore/Delete führen keine Archivoperation aus (`BackupsView.tsx:10`, `:63`, `:84`). |
| Zeitpläne | Beispieljobs und lokale Schalter, kein serverseitiger Scheduler. |
| Updates | Timer, erfundene Downloads/Prüfsummen/Snapshots und Versionswechsel ohne Installation (`UpdateManagerView.tsx:44`, `:70`). |
| Minecraft | Download installiert stets Paper; Enginewahl wird ignoriert. `26.*`, `Latest`, `snapshot` und unbekannte Versionen werden durch 1.21.4 ersetzt (`server.ts:168`). UI zeigt weiterhin die ursprüngliche Version. |
| Steam | Linux-SteamCMD-Download und einige native Linux-Binärnamen implementiert. Signalausgang fälschlich erfolgreich. Keine vollständigen spielabhängigen Adapter. |
| Windows/macOS/Docker | UI-Auswahl ersetzt keine Backendunterstützung. Frontend sendet Linux-Executable/-Argumente unabhängig von Ziel-OS (`App.tsx:252`). SteamCMD lädt Linuxarchiv (`server.ts:140`). Kein Container-/Remote-Node-Runner vorhanden. |
| Mods/Plugins | Suchproxies existieren; Installieren/Entfernen/Aktivieren nur Browserdaten, kein Dateidownload/-wechsel (`App.tsx:510`). Suche ist keine Installation. |
| Spieler | Beispielspieler und lokale Whitelist; behauptete RCON-Synchronisation ohne Implementierung (`PlayerManager.tsx`). |
| Messwerte | CPU/RAM/Netzwerk werden mit `Math.random()` verändert (`App.tsx:160`, `MetricsView.tsx:46`). Keine Hostmessung. |
| DNS/Subdomains | Lokale Erfolgsanzeige, kein DNS-Provider oder realer Node-/Portallocator (`NetworkPortsView.tsx`). |
| Discord | Test meldet HTTP 204 nach Timer, sendet keinen Request; Speichern nur Toast (`WebhooksView.tsx:39`). |
| Benutzer/RBAC | localStorage-Demoprofile; keine serverseitigen Benutzer-/Eigentümer-/Rechteobjekte (`data/authStore.ts:119`). |
| CRM/Shop/Prepaid | Browserzustand; Guthaben kann ohne Zahlungsdienst erhöht werden (`App.tsx:934`). Keine Zahlungstransaktionen, Gateway-Verifikation oder serverseitige Vertragsdurchsetzung. |

Die ursprünglichen Backend-Routen decken Diagnose, Logs, Power, Installation, Create, Konsole und vier Suchproxies ab. Datei-, Backup-, Spieler-, Benutzer-, Zahlungs-, Metrik-, Modinstallations- und Scheduler-APIs fehlen.

## Reparaturreihenfolge

1. API-Authentifizierung, echte Passwortprüfung, begrenzte Sitzungen, sichere Instanz- und Dateipfade; standardmäßig lokales Bind.
2. Prozessereignisse, Exit-Race, echte Neustarts/Kill, Sperren, Antwortprüfung und nachvollziehbarer Status.
3. Backend als maßgebliche Instanzdatenquelle; echte Dateiverwaltung und Konsole.
4. Echte Backups/Restore/Updates mit Fehlerbehandlung und Erhalt bestehender Daten.
5. Spiel-/Plattformadapter mit expliziten Fähigkeiten; keine stillen Versions- oder Enginewechsel.
6. Mods, Spieler, Zeitpläne, Metriken und Webhooks real anbinden oder klar als nicht verfügbar behandeln.
7. CRM/Zahlungen/RBAC als eigenständige produktive Funktionen implementieren und prüfen.

Die Komplexität liegt überwiegend in der Oberfläche. Das Projekt ist verwendbar als Ausgangsbasis, benötigt aber echte Backendfunktionen und passende Tests. Eine Zusicherung „alles fehlerfrei“ oder „alle Spiele unterstützt“ lässt sich aus dieser Prüfung nicht ableiten.
